## [v5.4.1] - Emergency Hotfix

### 🪲 Bug Fixes
- [Bugfix] **Commodore Elite Trait Was Cutting Shields by 90% Instead of Boosting Them by 10% (captainelitetraits.lua):** Player report: shields collapsing from full to near-nothing with no clear cause, ships getting one-shot that shouldn't have been. Root cause: `CosmicVaultBuffs.applyBuff`'s `multiplier` argument is a scale factor (`1.0` = unchanged, matching its documented "0.5 for half speed, 2.0 for double damage" contract), but the Commodore's "+10% Sector-Wide Shield and Damage" buff passed `0.10` for both the Shield and FireRate buffs. `cosmicbuff.lua` converts that into `delta = multiplier - 1.0 = -0.9`, so every player/alliance ship in a sector with a level-3 Commodore captain (a normal, common feature, not an edge case) had its Shield and FireRate cut by 90% instead of boosted by 10%, refreshed every 5-6 seconds for as long as the Commodore stayed in the sector. Fixed both calls to pass `1.10`.
- [Bugfix] **Station Governor's Shield Regen Bonus Did Nothing (stationgovernor.lua):** The Military Governor's "double shield regen rate" buff targeted `"ShieldRecharge"`, a stat name `cosmicbuff.lua` didn't handle (fixed in this same patch, see Cosmic Vault's changelog), and passed `1.0` as the multiplier, which is a no-op even once the stat name is fixed. Corrected to `2.0` to actually double the rate as advertised.

## [v5.4.0]

### 🪲 Bug Fixes

- [Bugfixed] **Offline Catch-Up (ARCC) Applied the Same Elapsed Time Repeatedly After a Server Pause (`player/background/simulation/simulation.lua`):** Reported by a singleplayer user: pausing the server correctly detected the elapsed real-world gap on resume, but then applied that same catch-up amount many times over (14 times in the reported case), finishing long-running fleet commands almost instantly. Root cause: `ARCC_applyCatchUpTime`'s own replay loop advanced simulated command time by calling `Simulation.update(nextStep)` — the ARCC-*wrapped* function, not the raw vanilla one — so every replay tick re-entered the same pause-gap detector that triggered the catch-up in the first place. Because `ARCC_lastUpdateClockTime` was only updated at the very end of the outermost `Simulation.update` call, each nested call made during the replay loop still read the same stale timestamp and the same large gap, so it computed and applied a fresh catch-up on top of the one already in progress — recursively, once per replay tick, until the loop happened to unwind. Fixed by having the replay loop call `ARCC_Simulation_update_original(nextStep)` directly, bypassing the ARCC wrapper (and its pause detection) entirely during replay — its only job is to advance simulated command state, not to re-run wall-clock detection against itself. Also moved `ARCC_lastUpdateClockTime`'s update to the top of `Simulation.update`, before any catch-up branch runs, as a second layer of protection against the same class of bug if the function is ever re-entered some other way in the future.
- [Bugfixed] **Automated Station-Network Trade Spammed "Trade Suspended" Chat Errors Every Tick (`entity/merchants/factory.lua`):** Reported by a player linking a Headquarters to several supply stations (e.g. a Wheat Farm needing Water + Energy Cells) via the delivery network: once any linked station sat in a `war_zone`/`cw_contested` sector, the player got repeated "Trade suspended! This station is under blockade due to an active war zone!" chat messages regardless of which sector they were actually in, and a Smuggler governor did nothing to stop it. Root cause: `Factory.buyGoods`/`Factory.sellGoods` are never reached via a real player-driven `invokeServerFunction` RPC anywhere in vanilla or this mod — the only call sites are automated, server-side `station:invokeFunction(...)` calls from the inter-station delivery network (`Factory.updateDelivery`, which vanilla's own `Factory.updateServer` runs every tick for docked partners) and from NPC/AI trading ships (`tradingutility.lua`). `Entity:invokeFunction` never sets `callingPlayer` (that's exclusive to `invokeServerFunction`), so `Player(callingPlayer)` inside the blockade guard was resolving against a stale/empty value — reliably enough, on a singleplayer or locally-hosted game (only one possible player, same degenerate case documented elsewhere for bare `Player()`), to fire a real chat message on every single automated trade attempt. The guard also had no Smuggler-governor bypass, unlike the separate siege-blockade check in `Factory.updateProduction`, and its bare `return` discarded the `(errorCode, price)` pair `Factory.updateDelivery`'s caller expects, so the per-partner delivery-error label showed a generic "Unknown error." on top of the chat spam. Replaced the chat message with a dedicated error code (`10`) returned normally through the existing delivery-error pipeline, added the missing Smuggler-governor bypass to match the sibling blockade check, and added `Factory.getBuyGoodsErrorMessage`/`Factory.getSellGoodsErrorMessage` overrides so the Factory Overview / delivery-error UI shows "Trade suspended: station is under blockade." instead of the generic fallback. No chat spam, and a Smuggler governor now correctly keeps automated trade running through a blockade, matching the production-halt check's existing behavior.
- [Bugfixed] **Factory Overview Status Column Always Read as "Running" (`entity/merchants/factory.lua`):** `Factory.updateProduction`'s override read `Factory.productionError` to determine each factory's current working state for the tab's Status column and tooltip. Cross-referencing vanilla's own `entity/merchants/factory.lua` confirmed vanilla never writes a `Factory.productionError` table field at all — the real state lives in file-scope locals `local productionError` / `local newProductionError` (~line 51). The only writer of `Factory.productionError` was this mod's own siege-blockade branch, and only when triggered, so the read evaluated to `nil` on virtually every tick, defaulting the Status column to "Running" regardless of the factory's actual state. Fixed by reading the bare local `newProductionError` instead, which is a valid upvalue for the override's functions since Avorion's VFS merges override content into the same compiled chunk as the vanilla file it replaces (the vanilla `local` declaration textually precedes the mod's appended functions, making it a normal Lua closure upvalue — the same mechanism already documented in `Avorion_Modding_Codex.md`'s "A local at file scope in vanilla shadows the global" section, applied here in the intended read direction rather than as an accidental collision).

- [Bugfixed] **Factory Overview Froze Permanently on Any Siege Blockade (`entity/merchants/factory.lua`):** `Factory.updateProduction`'s siege-blockade branch (`hostileStrength > friendlyStrength * 2`) executed an unconditional `return` immediately after flagging the blockade, skipping not just `base_updateProduction` (the intended "halt production") but also the entire telemetry/registration block below it (`fo_runtime`, `fo_productionStateRegister`, and the periodic `Factory.FactoryOverview_updateGalaxy` push to the galaxy registry). Any station that ever tripped an active Cosmic War blockade would freeze its Factory Overview row at its last pre-blockade values indefinitely, even after the blockade lifted, since nothing ever pushed fresh data again. Restructured with a `blockaded` boolean so `base_updateProduction` is still skipped (production genuinely halts, unchanged behavior) while the telemetry/registration block always runs when there's a valid player/alliance owner — the tab now correctly shows "Under Siege Blockade" as the dominant status instead of stale numbers.

- [Bugfixed] **Asteroid Mine Self-Healing Registration Was a Silent No-Op (`entity/merchants/factory.lua`):** `Factory.updateServer`'s self-healing block for neutral-claimed asteroid mines (mines whose `initialize()` fires before the player owns them) called `Galaxy():invokeFunction("galaxy/factoryregister.lua", "register", Entity().id)` — passing only 1 of the 3 arguments `register(factionIndex, allianceFactory, entity_data)` requires. With `entity_data` left `nil`, `register()`'s own guard clause (`if not entity_data then return end`) made the call a complete no-op every time. Compounding this, `Factory._co_registered` was set to `true` unconditionally after the attempt regardless of whether a valid faction was found, meaning the self-heal got exactly one try, on the very first `updateServer` tick — if the entity was still neutral at that exact moment (the entire scenario this code exists to catch), it would never retry once ownership was actually established. Fixed by reusing `Factory.FactoryOverview_updateGalaxy(faction.isAlliance)` (the same, correct factory-data construction the periodic path already uses) and only setting `Factory._co_registered = true` once a valid player/alliance faction is actually confirmed.

- [Bugfixed] **Factory Overview Tooltip Showed Untranslated Working-State Text (`player/ui/factory_overview_tab.lua`):** `getRowTooltip` built its per-row tooltip from `working_state`'s keys (the server-authored, plain-string `reason` values) without ever applying `%_t`, unlike every other server-authored display field in this file. Fixed to apply `%_t` once at the point of display, matching the convention already established for `factory['_statusReason']%_t` in `loadData`.

- [Bugfixed] **Factory Overview Could Resolve the Wrong Player on a Dedicated Server (`player/ui/factory_overview_tab.lua`):** `FactoryOverview.fetchDataFromGalaxy`'s server-side branch (an RPC target invoked via `invokeServerFunction`) resolved the requesting player with bare `Player()` — three separate times, for `.alliance`, `.index`, and `.allianceIndex` — while the same function's own `invokeClientFunction` call two lines later correctly used `Player(callingPlayer)`. Cross-referenced against vanilla's `player/ui/playerdiplomacy.lua` and `player/ui/alliancediplomacy.lua`, both of which explicitly resolve the calling player server-side via `Player(callingPlayer)`, never bare `Player()` — confirming this is the documented, engine-provided way to identify "the player who made this specific RPC call" (see `Globals.lua`'s `invokeServerFunction` doc comment: "a variable called 'callingPlayer' will be created or set before executing the called function"). On a singleplayer or hosted game there's only ever one player to resolve to, so this went unnoticed; on a real dedicated server with several players calling this concurrently, bare `Player()` has no such guarantee. Fixed by resolving `Player(callingPlayer)` once into a local and using it for all three reads.

- [Bugfixed] **Dedicated Server Crash Risk: `%_t` at Unguarded Global Scope, Latent (`lib/galaxymapqolclient.lua`):** This client-only UI library builds its `bossDistances` table using `%_t` at true module scope, with no guard of its own. Its only current `include()` site (`player/map/galaxymapqol.lua`) already wraps the call in `if onClient() then`, so this was not actually reachable server-side today — but that safety depended entirely on every future includer remembering the same guard, with no protection in the library itself. Added `if onServer() then return end` at the top of the file, per the standing rule for pure UI scripts in `Avorion_Modding_Codex.md`'s "UI Development" section, so the file is safe regardless of how it's included in the future.

### ⭐ Quality of Life

- [QoL] **Factory Overview Live Auto-Refresh (`player/ui/factory_overview_tab.lua`):** Added `FactoryOverview.getUpdateInterval()` (10s, matching the server's own `fo_refreshFrequency` push cadence) and `FactoryOverview.updateClient(timeStep)`, following the same pattern as vanilla's `player/ui/sectorshipoverview.lua` (`self.window.visible` guard). Data now refreshes automatically every 10 seconds while the Factory Overview tab is the one actually visible/active (`self.tab.visible` and `self.tab.isActiveTab`), instead of only on tab-select/show or a manual Refresh click.

- [Adjustment] **Factory Overview Status Column Now Uses a Rolling 30-Minute Window Instead of Lifetime Average (`entity/merchants/factory.lua`, `galaxy/factoryregister.lua`):** The Status column's working-state breakdown (`fo_productionStateRegister`) previously accumulated from the moment the entity script loaded and never reset, so a factory that ran fine for hours before getting stuck would still show close to 100% Running for a long time afterward — new problems were diluted into invisibility by old history. Added `fo_statusWindowRuntime` (a separate counter from `fo_runtime`, kept independent so the profit/hour calculation in `factoryregister.lua`'s `calculateProfitability` — which needs true lifetime runtime — is unaffected) and reset both it and `fo_productionStateRegister` every 1800 seconds (30 minutes). `factoryregister.lua`'s `addWorkingStrings` now uses the new `status_window_runtime` field as its percentage denominator (falling back to the legacy `runtime` field if absent, for safety against any not-yet-refreshed cached data).

- [Adjustment] **Factory Overview Telemetry Now Persists Across Sector Unloads/Server Restarts (`entity/merchants/factory.lua`):** `fo_runtime`, `fo_productionStateRegister`, `fo_statusWindowRuntime`, and `Factory._co_registered` were plain locals/fields never included in `Factory.secure()`/`Factory.restore()`, so they silently reset to their defaults every time the entity script reloaded (sector unload, server restart) even though nothing about the factory's actual history changed. Added all four to the secure/restore round-trip.

### 🎨 UI/Structural Overhaul (Resource Display, Bulletin Board, Galaxy Map QoL)

Builds on the new Cosmic Vault UI Kit (`cosmicvaultuikit.lua`/`cosmicvaultsettingsschema.lua`, Cosmic Vault v3.6.0 — see that mod's own changelog) so these three features share the same layout/table/status-color/settings foundation instead of each hand-rolling its own, and so future Cosmic mods can build consistent UI on the same base.

- [Adjustment] **Resource Display Settings Moved onto Cosmic Vault's Settings Schema API (`player/ui/resourcedisplay.lua`):** The 9 HUD settings (`CO_RD_Enabled`, `CO_RD_PosX/PosY`, `CO_RD_Cargo`, `CO_RD_Inv`, `CO_RD_InvBoth`, `CO_RD_Alli`, `CO_RD_BgOp`, `CO_RD_CmpNum`) were each hand-plumbed through a separate client-side read, a separate toggle handler, and a separate server-side save call, with the server's only validation being a loose `string.sub(key, 1, 6) == "CO_RD_"` prefix check that would accept any similarly-prefixed key rather than a known one. Replaced with one `CosmicVaultSettingsSchema.define(...)` call (`{key, default, type}` per setting) backing real key/type validation on every write. Existing players' saved settings are preserved: the schema's own storage location is a new, prefixed key, so the client-side read checks that location first and falls back to the exact pre-existing raw key of the same name — a returning player's HUD preferences load correctly either way, and future writes land in the new location. Also deduplicated the alliance-vs-personal display selection for the resources block into a small `pickDisplayFaction` helper (the inventory block's own toggle has different semantics — "show both" rather than "show alliance instead of personal" — and was deliberately left as its own logic rather than forced through the same helper), and fixed a leftover hardcoded alliance-prefix string literal that should have reused the already-computed `prefix` value.

- [Bugfixed] **Illegal `callable(nil, ...)` Inside Namespaced `BulletinBoard` Script (`entity/bulletinboard.lua`):** This override re-registered `acceptMission` via `callable(nil, "acceptMission")`, even though it reuses vanilla's namespaced `BulletinBoard` table (`-- namespace BulletinBoard`) and vanilla itself already registers the same function correctly via `callable(BulletinBoard, "acceptMission")`. Per the project's own linter rule for namespaced scripts, `callable(nil, ...)` registers into the unrelated global `Callable` table instead of the namespace's own — fixed to `callable(BulletinBoard, "acceptMission")`.

- [Bugfixed] **Galaxy Map QoL: Namespace-Shadowing Global Wrappers Around Every Lifecycle Callback (`lib/galaxymapqolclient.lua`):** The single most severe finding of this pass. This file has no `-- namespace` declaration of its own, but it is `include()`'d only from `player/map/galaxymapqol.lua`'s client branch — and that file declares `-- namespace GalaxyMapQoL`. Since `include()` executes a file's code directly into the includer's own environment, nine bare global functions at the bottom of this file (`initialize`, `getUpdateInterval`, `updateClient`, and six `galaxyMapQoL_on*` event handlers), each just forwarding to the identically-named `GalaxyMapQoL.*` method, were shadowing the namespace-table methods the engine already auto-routes lifecycle and event callbacks to — exactly the "catastrophic runtime failures in event synchronization" class of bug the project's own engine-constraints documentation warns namespaced scripts about. Confirmed safe to delete outright (not rename) against vanilla's own `player/ui/sectorshipoverview.lua`, which registers `player:registerCallback("onStateChanged", "onPlayerStateChanged")` and resolves it straight to the namespaced `SectorShipOverview.onPlayerStateChanged` with zero bare-global wrapper anywhere in that file — the identical pattern this same file already uses correctly for its own `registerCallback` calls in `GalaxyMapQoL.initialize()`. Also removed three stray `callable(nil, "sync"/"syncWarZones"/"setSectorIcon")` calls sitting just above the wrapper block (harmless — the real, correct registrations already exist server-side in `player/map/galaxymapqol.lua` as `callable(GalaxyMapQoL, ...)` — but redundant and confusing to leave in place). This was not something we set out looking for; it surfaced while checking a much smaller, already-known issue in the same file.

- [Bugfixed] **Galaxy Map QoL: `deleteUndo` Was an Accidental Global (`lib/galaxymapqolclient.lua`):** Used throughout the file (the undo stack for deleted map icons) but never declared `local` — a genuine, if lower-severity, leak into the shared script environment. Added to the file's existing `local` declaration block; confirmed nothing outside this file references it.

- [Adjustment] **Galaxy Map QoL: Removed the Unused `GalaxyMapQoLIntegration.lua` Extension Point:** `addIcons(...)` (for registering custom map icons from another mod) and `GalaxyMapQoL.initOtherNamespace` (for letting another mod's namespace adopt these callbacks directly) had zero callers anywhere in this workspace. Removed the file and every reference to it (`lib/galaxymapqolclient.lua`, `player/map/galaxymapqol.lua`), including the now-pointless `customNamespace`/`galaxyMapQoL_updateClient` state that only existed to support `initOtherNamespace`. The server-side icon-name whitelist that `Integration` fed into (used to validate a client's `setSectorIcon` RPC) is untouched — only the always-empty custom-icon injection point is gone.

- [Adjustment] **Galaxy Map QoL: Deduplicated the Three Overlay Toggle Functions' Deselect Behavior:** `onResourcesOverlaySelected`, `onTechLevelsOverlaySelected`, and `onBossesOverlaySelected` each repeated an identical 8-line "clear custom colors and hide the legend" block when turning an overlay off. Extracted into one `clearOverlayDisplay()` helper. Deliberately did **not** unify the "turn on" branches — each builds its overlay data in a genuinely different shape (per-material distances, per-tech-level colors, per-boss min/max ranges with alternating colors), and forcing them through one signature would add indirection without removing any real duplication.

- **Scope note on this file:** `lib/galaxymapqolclient.lua` (1600+ lines, ~20 interdependent module-scope UI state variables spanning the icon editor, drag-select, and rendering) was originally planned to also be split into focused sub-modules and have its config storage moved onto the new Settings Schema API. Neither happened in this pass, deliberately. The config (`playerIcons`, `colors`, `deleteUndo`, etc.) holds structured tables, not the scalar bool/number/string values `CosmicVaultSettingsSchema` is built for, so forcing it through that API would be a poor fit, not an improvement — its existing `Azimuth.loadConfig`/`saveConfig` mechanism already suits this shape correctly. The full module split was set aside because this file's state is far more tightly interdependent than Bulletin Board's or Resource Display's, this can't be tested in an actual running game before shipping, and a mistake here has a larger blast radius (the whole Galaxy Map QoL feature, not one tab) than getting Bulletin Board's table wrong. The two `GameVersion() >= Version("2.0")` options-panel layouts were left untouched for the same reason. Fixing the confirmed namespace-shadowing bug and removing genuinely dead code were worth doing regardless of testing risk; restructuring 1600 lines of tightly-coupled UI state without being able to verify it in-game was not.

## [v5.3.1]

### 🪲 Bug Fixes

- [Bugfixed] **Dedicated Server Crash: `%_t`/`%_T` at Unguarded Global Scope (`scoutcommandnotetable.lua`, `managestationincomes.lua`):** Both files built a Lua table using the `%_t`/`%_T` translation operator directly at module top-level (true global scope, not inside any function or `if onClient()` guard). A dedicated server evaluates a script's top-level statements immediately as the file loads, and the server's Lua state never binds the UI localization metatable those operators dispatch through — so this crashes the server the instant either file is loaded. `scoutcommandnotetable.lua` is `include()`'d unconditionally from `scoutcommand.lua` (a server-authoritative background-simulation script, confirmed via its own `:getLines()` call site), and `managestationincomes.lua` is forced server-only by its own `if not onServer() then return end` guard — both are genuinely server-reachable, not client-only. Fixed by wrapping `scoutcommandnotetable.lua`'s entire `SectorClassNoteLineTable` builder chain in an immediately-invoked function (`return (function() ... end)()`), and by moving `managestationincomes.lua`'s `stationMappings` table literal into a new `ManageStationIncomes.buildStationMappings()` function called once from `initialize()` — both keep identical behavior/timing while moving the `%_t`/`%_T` evaluation into function scope, which is safe per the documented rule (see `Avorion_Modding_Codex.md`'s "UI Development" section, and the correction added there in the same pass: the earlier "fatal syntax error" framing was wrong — it's a runtime error that fires the moment the offending line executes, not a parse-time failure).

- [Bugfixed] **Duplicate `managestationincomes.lua` Reconciled — Merchant Governor Income Bonuses Restored:** `data/scripts/sector/managestationincomes.lua` and `data/scripts/entity/merchants/managestationincomes.lua` had existed as two independently-edited forks of the same station-income system since early in the mod's history, and were never reconciled. Only the `sector/` copy was ever wired up (`sector:addScriptOnce(...)` in `sector/init.lua`); the `entity/merchants/` copy kept receiving edits despite never actually running. Git history confirms the `entity/merchants/` copy was the only one implementing the Station Governor Merchant income bonuses (`governor_merchant_active`, set by `stationgovernor.lua`) documented in the Wiki and Player Guide under "👔 Station Governors" (+25% passive station income, +50% AI traffic) — meaning that documented bonus has had no effect in actual gameplay for as long as the two files have diverged. Consolidated to a single file, kept at `data/scripts/sector/managestationincomes.lua`: this is a sector-level aggregator (`sector:addScriptOnce`, `updateServer`/`getUpdateInterval` registered as sector lifecycle hooks, one script instance iterating every station in the sector via `Sector():getEntitiesByType(EntityType.Station)`), not a per-entity script — the same architectural pattern as this mod's own `sector/co_famine_listener.lua` and vanilla's own sector-folder aggregators (`traders.lua`, `xsotanswarm.lua`, `eventscheduler.lua`, `points.lua`), unlike vanilla's `entity/merchants/casino.lua`, which is a per-station entity script and not a real precedent for this file's location. Kept the `sector/` fork's newer balance logic (300% max War Profiteering multiplier, Core-Distance income multiplier, `faction:receiveResource(...)` instead of the older `faction:receive(msg, 0, unpack(args))`) and restored all three governor bonus checks from the `entity/merchants/` fork: +25% resource yield in `giveStationResources`, +25% money in `giveStationMoney`, and a trade-frequency boost in `manageStation`. `data/scripts/entity/merchants/managestationincomes.lua` deleted (after a brief detour where the consolidated file was placed there instead — moved back to `sector/` once the architecture mismatch was caught).

- [Bugfixed] **Governor Trade-Frequency Bonus Was Backwards:** While restoring the trade-frequency bonus above, found that the original `entity/merchants/` formula (`chance = chance * 1.5`) had the wrong direction. `mapping.chance` is a *skip* probability — `random():test(mapping.chance)` returning true means the station skips giving income this cycle — so multiplying it by 1.5 made a governed station skip *more* often, i.e. trade *less* frequently, the exact opposite of the code's own comment ("50% more frequent trader traffic / payouts") and the Wiki's "+50% AI traffic" claim. Confirmed against the `Random:test(probability)` stub (`Avorion Stubs/Random.lua`) and the inverse `chance`/`quantity` relationship across every entry in `stationMappings` (e.g. Repair Dock: low chance 0.2, high quantity 3.0 — skips rarely, pays a lot when it does). Fixed by scaling the *success* rate (`1 - chance`) up by 1.5× instead, capped at 100%, then deriving the boosted skip chance from that.

### ⭐ Feature Overhauls
- [Feature] **Command Center Tab Completely Overhauled (`command_center_tab.lua`):** The original Command Center only listed active background/physical ship operations with no sorting, no filtering, and no financial context — largely redundant with vanilla's own Fleet window. Rebuilt into a dedicated Fleet Operations & Earnings Dashboard: (1) a new **Fleet Income** tracker shows cumulative credits earned through background commands, aggregated across the player's own faction and their alliance, with a manual reset button — backed by two new hooks in `simulation.lua`'s existing monkey-patch layer (`ARCC_trackFleetIncome`, wired into both the immediate-delivery payout path and a new wrapper around vanilla's `Simulation.takeYield`, so both ways a background command can actually pay out are captured); (2) idle ships (ones with no active order at all) are now surfaced as their own rows instead of being silently skipped, so the tab can answer "which of my ships are doing nothing" — something vanilla's Fleet window doesn't call out; (3) an **Attention Needed** strip shows live counts of Idle / Completing Soon (ETA under 60s) / Recalled ships, each clickable to jump straight to that filter; (4) the operations table is now sortable by every column (Ship/Operation/Location/ETA/Status), defaulting to soonest-ETA-first; (5) the header layout was decluttered onto separate rows so controls no longer share horizontal space and risk overlapping on a narrower player window, matching the layout pattern already used elsewhere in the Cosmic series. Also fixed three latent correctness bugs found while rebuilding the file: `invokeFunction`'s first return value is a call-status code (0 = success), not a boolean, so the original `if not ok then` guard could never actually detect a failed call (every Lua number, including 0, is truthy); several server-authored strings were being wrapped in the network-deferred `%_T` marker and then re-translated client-side with `%_t`, instead of being sent as plain strings and translated once on receipt (the correct, established convention already used by other Cosmic mod UI tabs) — non-English clients could have seen incorrectly or doubly-resolved text in the operation list; and `Player:getShipNames()` was captured into a single local (`local shipNames = player:getShipNames()`) and gated on `type(shipNames) == "table"` — the engine's own generated API docs and every real vanilla call site (`simulation.lua`, `mapcommands.lua`, `repairdock.lua`, etc.) confirm it actually returns a vararg of strings, not a table, so the unwrapped capture silently truncated to just the first ship name and the `"table"` type check then always failed, meaning the physical-ship/idle-ship listing (including the brand new Idle Ships feature above) never actually ran. Fixed by wrapping the call in `{ player:getShipNames() }`, matching the established vanilla convention.
- [Feature] **Factory Overview Tab Enhanced (`factory_overview_tab.lua`):** Added a **Location** column (the factory's sector coordinates, previously only usable indirectly via "Goto Selected") and a **Status** column showing the dominant working-state reason and the percentage of time spent in it (e.g. "94% Running" in green, "62% Missing Ingredients" in red), computed from the same `working_state` breakdown already shown in each row's tooltip — so a stalled or underperforming factory is now visible without hovering every single row, matching this tab's own documented goal of "highlighting supply blocks and underperforming installations instantly." Both new columns are fully sortable, alongside the existing five. Also added a **Totals** summary in the header showing aggregate Income/Expense/Profit across every factory currently shown (respecting the Alliance toggle), and decluttered the header onto two rows so the title/totals no longer share space with the Refresh/Goto/Alliance controls.
- [Feature] **Fleet Status Screen (FSS) Overhauled (`data/scripts/entity/fleetstatus.lua`):** This standalone Player UI window (opened from a ship, not a Player Window tab — deliberately kept that way) tracks shield/hull status for any of your ships you choose to pin to the HUD.
